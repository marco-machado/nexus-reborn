### Follow-up: the 41.7 ms live-play frame (investigated and fixed, same day)
The user said "investigate and fix it".

**Where.** A mission-only probe logged every live frame over 20 ms against sim time and the comm log. 2 of 3 runs hit one at sim 12 s (25.1, 33.2 ms), the frame where "Reach the checkpoint gate" completes and "Eliminate the CorpSec garrison" activates. No long task (> 50 ms) overlapped it.

**Why.** A Chrome trace (renderer main thread, CPU sampling) across sim 10–14 s:
- Every 200 ms there is a ~10 ms main-thread task: `world.ts` pushes fresh squad rows every `SYNC_INTERVAL` (0.2 s), and the whole `Hud` re-renders, including four `Portrait` SVGs whose content has not changed (Hud ≈ 30 %, Portrait ≈ 20 % of samples).
- At the objective switch, extra store writes (objectives, two log lines) bunch these into 8.5–11.3 ms tasks back to back, plus one 20.2 ms task. At 120 Hz (8.3 ms frames) that drops 2–4 frames.
- The run is on the dev server (React dev build, StrictMode), so the absolute cost is higher than in a production build. The smoke frame check is defined on the dev server.

**Fix** (UI only; sim, stores and the push cadence unchanged):
- `src/ui/Hud.tsx`: the squad card is a memoized `SquadRow`; it re-renders only when its own values, selection, active state or portrait inputs change.
- `src/ui/squadRows.ts` (new): the by-value comparison. `src/ui/squadRows.test.ts` (new, 12 tests) covers it.
- `src/ui/portrait.tsx`: `Portrait` is memoized by value (`id`, `codename`, `accent`, `size`), so callers that build a fresh op object skip the SVG rebuild.
