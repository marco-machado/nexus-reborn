# Bug Report

## Summary
**Title**: Closing Settings opened from the Menu leaves focus on the page body, not the SETTINGS button
**ID**: BUG-0002
**Severity**: S3-Medium
**Priority**: P1-Fix this sprint
**Status**: Open
**Reported**: 2026-10-19
**Reporter**: —

> qa-lead set Severity and Priority at the /team-qa Phase 5 review (R4 in `production/qa/evidence/team-qa-2026-10-19-s9/qa-lead-review.md`).
> - **S3-Medium**: keyboard access is degraded but not lost. After the close, focus sits where a keyboard user cannot act. Whether Tab from the start of the document reaches the Menu buttons again was **not verified**.
> - **P1-Fix this sprint**: this fails a ticked AC (IF-005 AC19) in a Complete story at qa.level standard.

## Classification

- **Regression**: Unknown. The IF-005 smoke capture (`production/qa/evidence/smoke-2026-10-19/if-005/capture-output.txt`) only exercises Settings opened from pause. The evidence checked holds no earlier passing observation of the Menu path.

- **Game State**: Fresh profile (localStorage cleared). No campaign save.

## Reproduction Steps
**Preconditions**: A fresh profile (localStorage cleared), with the Menu loaded and no dialog open.

1. Focus the Menu's SETTINGS button (aria-label `OPEN SETTINGS // AUDIO, CONTROLS AND ACCESSIBILITY`) and press Enter. The Settings dialog opens with focus inside it, on CLOSE.
2. Press Tab 30 times. Focus stays inside Settings.
3. Press Escape to close Settings. Check `document.activeElement`.
4. Repeat steps 1-2. Then focus the Settings CLOSE button and press Enter. Check `document.activeElement` again.

**Expected Result**: After each close, focus returns to the SETTINGS button (`OPEN SETTINGS // ...`). IF-005 AC19: "GIVEN Pause or Settings, WHEN Tab/Shift+Tab and close are exercised, THEN focus stays trapped while open and returns to the opening context when closed". GDD `design/gdd/interface.md:73` (§14): "Pause and Settings trap and restore focus (including nested Settings return)."

**Actual Result**:
- Opening Settings and the Tab trap both pass, for both close methods.
- After both the Escape close and the CLOSE close, focus is not on the SETTINGS button: `document.activeElement` is the page body.
- Verified on a second run (2026-10-19) after the probe was changed to log the tag. Both closes recorded `{"tag":"BODY","isBody":true}` (`document.activeElement === document.body`). The open and the trap recorded `{"tag":"BUTTON","label":"CLOSE","inSettings":true}`. Reproduced 2 of 2 attempts on each of the two runs.
- There are 0 page errors (`errors: []`).

**Contrast (the same build passes these paths)**: `production/qa/evidence/smoke-2026-10-19/if-005/capture-output.txt`:
- Line 31: closing pause returns focus to the control that opened it ("Pause and open the menu").
- Line 30: closing Settings opened from pause returns focus to the pause modal.

## Technical Context
- **Likely affected files**:
  - `src/ui/index.tsx:236-240`: the Menu SETTINGS button, `onClick={act(() => setSettingsOpen(true))}`. The Menu is the only Settings entry point outside pause.
  - The Settings dialog's close and focus-restore path. This run did not locate it.
- **Related systems**: Menu, Settings overlay, the pause modal (its focus restore works), `appStore` overlay state.
- **Possible root cause**: Not traced.
- **Recommended fix** (for the programmer to decide): on close, return focus to the control that opened Settings, as the pause path already does. Add a regression test for Settings opened from the Menu.
